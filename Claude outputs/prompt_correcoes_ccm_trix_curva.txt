4. Achado técnico — converter_seed_ccm.py: mapeamento de colunas frágil, sem validação
------------------------------------------------------------------------------------------

O código atual identifica a coluna High procurando a letra "x" no nome da coluna do
Excel (`elif "x" in c_lower: col_map[col] = "High"`, com Low como "else" — tudo que
sobra). Isso só funciona hoje porque, por coincidência de português, "Máxima" contém
"x" e "Mínima" não. Não há nenhuma verificação de que o mapeamento resultou correto.

Corrigir para:
  a) Mapear as colunas por nome completo esperado (com tolerância a acento/caixa,
     mesmo padrão defensivo já usado em leitor_csv.py deste projeto — reaproveitar a
     lógica, não reinventar), não por substring genérica de uma letra.
  b) Depois da conversão, validar programaticamente que High >= Open, Close, Low e
     Low <= Open, Close para 100% das linhas — se falhar, o script deve parar com
     erro claro, nunca gravar um seed com colunas potencialmente trocadas.
  c) Se o Excel de origem mudar o texto do cabeçalho no futuro (novo export do
     Profit), o script deve falhar de forma explícita (coluna esperada não
     encontrada), nunca silenciosamente mapear errado.

5. Achado técnico — janela de contágio de trix/trix_sinal foi decidida sem consulta
------------------------------------------------------------------------------------------

Em classificar_proveniencia(), o código fixa uma janela de contágio de 21 pregões
para "trix" e 24 para "trix_sinal" (dict `janelas`), tratando esses valores como
DERIVADO assim que 21/24 pregões reais se passam da costura do seed. Isso não estava
no prompt original — o prompt só especificava a janela de 100 pregões para
trend_sma100/posicao_trix_v5. TRIX é uma tripla EMA(7); uma média móvel exponencial
tem memória que decai mas não zera numa marca fixa de barras — usar 21/24 como corte
é uma aproximação razoável na prática, mas foi uma decisão de modelagem tomada sem
perguntar, o que o próprio prompt original proibia (seção 4: "não decidir sozinho
nenhum parâmetro" / seção 1.8: "na dúvida, pare e pergunte antes de codar").

Não estou pedindo para mudar o valor agora — é uma aproximação aceitável. Estou
pedindo para documentar explicitamente, no próprio código (docstring de
classificar_proveniencia()) e na tabela_proveniencia.md, que esse corte de
21/24 pregões é uma convenção arbitrária (não vem do NTSL nem do prompt original) e
qual foi o raciocínio para escolher esses números especificamente. Se não houver
raciocínio quantitativo por trás, usar o mesmo critério do trend_sma100 (100
pregões) para trix/trix_sinal também, por consistência, e registrar a mudança.

6. Achado técnico — tabela_proveniencia.md promete uma distinção que o código não faz
------------------------------------------------------------------------------------------

A tabela de proveniência entregue (linha "Preço Candle (Open)") descreve a
classificação do campo Open no primeiro pregão real como "MEDIDO / ESTIMADO", com a
justificativa de que, nesse dia específico, o valor de Open é herdado do último
Close do seed (portanto deveria ser ESTIMADO). Mas o código real de
classificar_proveniencia() não implementa essa exceção — ele classifica Open como
qualquer outra coluna de preço, sempre MEDIDO quando is_sintetico=False naquele dia,
sem checar se o valor herdou algo do trecho sintético.

Resolver de um dos dois jeitos (documentar qual foi escolhido):
  a) Implementar a exceção no código: Open do primeiro pregão real classificado como
     ESTIMADO (porque seu valor vem do Close do dia sintético anterior), com a
     tabela ficando como está; ou
  b) Simplificar a tabela para bater com o código real: Open do primeiro pregão real
     também MEDIDO, com nota explicando que o proxy de Open é sempre calculado sobre
     o Close do pregão anterior (real ou sintético) e essa nuance específica não é
     rastreada separadamente.
Qualquer uma das duas é aceitável — o que não é aceitável é a documentação descrever
um comportamento que o código não tem. Isso é exatamente o tipo de coisa que a
auditoria da seção 7 do prompt original existe para pegar ("a tabela de proveniência
bate com o código real, não com o texto que a descreve").
